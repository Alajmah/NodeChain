# v3.5 Invariants — Retry-Authorized Side-Effect Execution

Introduced: 2026-07-11
Design basis: `docs/design/retry-authorized-execution.md` (48-point lock, 5 review rounds)
Companion plan: `docs/superpowers/plans/2026-07-11-v3.5-retry-authorized-execution.md`

These invariants are the normative spine. They are derived from the 48-point locked design but written as independent statements that can be understood and enforced without reading the design debate. Implementation decisions (DEC-xxx) are kept separate at the end of this file.

---

## INV-001: Two-Row Retry Lineage

Introduced: 2026-07-11
Status: ACTIVE
Scope: side-effect recovery

Statement:
Every executed retry authorization creates a distinct child attempt row.
The original `retry_authorized` side-effect row is never reused as the retry attempt.

Rationale:
Authorization is not execution. Historical outcomes must not be rewritten.

Depends_on: []

Primary_enforcement: db_constraint
  - UNIQUE(run_id, recovery_decision_id) on side_effect_ledger

Defense_in_depth: runtime_guard
  - SideEffectRetryCoordinator._allocate_child_attempt()

Failure_codes:
  - RETRY_DECISION_ALREADY_BOUND

Verified_by:
  - test_inv_001_allocates_distinct_child
  - test_inv_001_parent_status_remains_retry_authorized
  - test_inv_001_decision_cannot_allocate_second_child

## INV-002: Deterministic Key Binding

Introduced: 2026-07-11
Status: ACTIVE
Scope: side-effect recovery

Statement:
A retry child attempt key is deterministically derived from
(parent_side_effect_key, recovery_decision_id).
One recovery decision binds to at most one child attempt.
Duplicate execution commands converge on the same child row.

Rationale:
Prevents command replay from creating a second child and executing twice.

Depends_on: [INV-001]

Primary_enforcement: db_constraint
  - UNIQUE(run_id, recovery_decision_id)

Defense_in_depth: runtime_guard
  - make_retry_side_effect_key() is the sole canonical key constructor

Failure_codes:
  - RETRY_DECISION_ALREADY_BOUND

Verified_by:
  - test_inv_002_duplicate_command_converges
  - test_inv_002_key_is_deterministic

## INV-003: Parent Permanently Immutable After Child Allocation

Introduced: 2026-07-11
Status: ACTIVE
Scope: side-effect recovery

Statement:
Once a child attempt is allocated, the parent side-effect row's status
is permanently immutable. No subsequent action may transition the parent
to completed, failed, or any other status. This immutability does NOT
end when the child becomes terminal.

Rationale:
The parent records historical truth: an effect became unknown and was
authorized for retry. Changing that record rewrites history.

Depends_on: [INV-001]

Primary_enforcement: runtime_guard
  - SideEffectRetryCoordinator rejects parent-mutating actions
  - Store invariant: parent status mutation checks for retry lineage
    inside the same transaction

Defense_in_depth: runtime_guard
  - RecoveryService.apply_action early rejection

Failure_codes:
  - RECOVERY_TARGET_IN_FLIGHT (child is planned or started)
  - RECOVERY_TARGET_HAS_RETRY_LINEAGE (child is terminal)

Verified_by:
  - test_inv_003_parent_immutable_while_child_planned
  - test_inv_003_parent_immutable_while_child_started
  - test_inv_003_parent_immutable_after_child_terminal

## INV-004: Pre-Dispatch Capsule Prerequisite

Introduced: 2026-07-11
Status: ACTIVE
Scope: side-effect lifecycle

Statement:
No governed side effect may transition to `started` unless its replay
capsule was durably persisted first. Capsule persistence and the
planned-to-started transition are atomic. No capsule means no dispatch.

Rationale:
The crash window opens at dispatch. Without a pre-dispatch capsule,
retry material may be permanently lost if the effect becomes unknown.

Depends_on: []

Primary_enforcement: runtime_guard
  - SideEffectJournal._journal_one() capsule write before started transition

Defense_in_depth: db_constraint
  - Capsule row foreign key on side-effect ledger row

Failure_codes:
  - REPLAY_CAPSULE_PERSISTENCE_FAILED

Verified_by:
  - test_inv_004_capsule_commits_before_started
  - test_inv_004_no_capsule_blocks_dispatch

## INV-005: Recovery Execution Seam is Distinct

Introduced: 2026-07-11
Status: ACTIVE
Scope: runtime architecture

Statement:
Normal chain execution and recovery execution are distinct runtime models.
The typed-port orchestrator loop advances chain state and routes outputs.
The recovery seam executes a specifically authorized historical side effect
without advancing the chain graph. Neither path re-enters the other.

Rationale:
The typed-port loop (forward flow, downstream routing, port matching) and
recovery execution (backward lineage, exact-request gating, dispatch
fencing) are incompatible execution models.

Depends_on: []

Primary_enforcement: runtime_guard
  - SideEffectRetryCoordinator invoked through a separate call path
  - RecoveryRuntimeGate interceptor registered only during recovery invocations

Defense_in_depth: none

Failure_codes:
  - N/A (architectural boundary)

Verified_by:
  - test_inv_005_recovery_does_not_enter_typed_port_loop
  - test_inv_005_recovery_gate_unregisterd_after_invocation

## INV-006: Exactly One Target Effect Per Recovery Invocation

Introduced: 2026-07-11
Status: ACTIVE
Scope: side-effect recovery

Statement:
Tier 1 recovery permits exactly one governed side-effect proposal:
the authorized target. Any non-target governed operation — including a
read-only one — is rejected before dispatch. No ancillary-effect exception
exists in v3.5.

Rationale:
Recovery is not a miniature typed-port execution loop. Introducing
sanctioned secondary effects creates a recovery subgraph before the
single-operation model has been proven.

Depends_on: [INV-005]

Primary_enforcement: runtime_guard
  - RecoveryRuntimeGate rejects any non-target proposal before dispatch

Defense_in_depth: runtime_guard
  - max_total_side_effects: 1 in execution_constraints

Failure_codes:
  - SIDE_EFFECT_RETRY_REJECTED

Verified_by:
  - test_inv_006_second_effect_rejected
  - test_inv_006_read_only_secondary_rejected

## INV-007: Recovery Child Uses Normal Lifecycle

Introduced: 2026-07-11
Status: ACTIVE
Scope: side-effect recovery

Statement:
Every retry child attempt enters the normal side-effect lifecycle at
`planned` and transitions through `started` to `completed`, `failed`,
or `unknown`. No child begins at `retry_authorized`. No child skips
`planned`.

Rationale:
The child is a real execution attempt, not an authorization. It earns
its terminal state through the same observed-completion discipline.

Depends_on: [INV-001]

Primary_enforcement: db_constraint
  - LEGAL_TRANSITIONS (with retry_authorized→started removed)

Defense_in_depth: runtime_guard
  - SideEffectRetryCoordinator allocates child at planned

Failure_codes:
  - SideEffectTransitionError

Verified_by:
  - test_inv_007_child_starts_at_planned
  - test_inv_007_child_transitions_through_normal_lifecycle

## INV-008: Dead Transition Removed

Introduced: 2026-07-11
Status: ACTIVE
Scope: side-effect state machine

Statement:
The `retry_authorized → started` transition is removed from
LEGAL_TRANSITIONS. The state machine encodes the invariant; it does not
merely document it.

Rationale:
Leaving a legal but forbidden transition creates a latent same-row retry
path that a future caller may accidentally activate.

Depends_on: [INV-007]

Primary_enforcement: db_constraint
  - retry_authorized removed from LEGAL_TRANSITIONS target sets

Defense_in_depth: runtime_guard
  - Transition validation rejects retry_authorized→started

Failure_codes:
  - SideEffectTransitionError

Verified_by:
  - test_inv_008_retry_authorized_to_started_rejected

## INV-009: Three Independent Truths

Introduced: 2026-07-11
Status: ACTIVE
Scope: operator surfaces

Statement:
Node invocation outcome, child side-effect outcome, and operator-action
outcome are independent operator-visible truths. None may overwrite
another. A failed recovery invocation does not falsify a completed child.

Rationale:
The three records answer different questions: did the node obey its
contract? what happened to the external operation? did the command
succeed? Conflating them violates trace truth.

Depends_on: [INV-006]

Primary_enforcement: runtime_guard
  - RecoveryService records each outcome in its own record
  - Inspect displays all three independently

Defense_in_depth: none

Failure_codes:
  - N/A (observability invariant)

Verified_by:
  - test_inv_009_three_truths_displayed_independently
  - test_inv_009_failed_invocation_preserves_completed_child

## INV-010: Completed Child Does Not Mutate Chain State

Introduced: 2026-07-11
Status: ACTIVE
Scope: chain isolation

Statement:
A completed retry child does not replace the original invocation output,
write to ChainState.outputs, route data through downstream typed ports,
unskip downstream nodes, resume the orchestrator loop, mark the chain
completed, or mark the parent side-effect completed.

Rationale:
v3.5 is side-effect retry execution and observation, not chain recovery.

Depends_on: [INV-001]

Primary_enforcement: runtime_guard
  - RecoveryService does not touch ChainState.outputs or chain status

Defense_in_depth: none

Failure_codes:
  - N/A (scope invariant)

Verified_by:
  - test_inv_010_chain_outputs_unchanged_after_retry
  - test_inv_010_chain_status_unchanged_after_retry

## INV-011: Dispatch Boundary Marker is Truthful

Introduced: 2026-07-11
Status: ACTIVE
Scope: crash recovery

Statement:
`dispatch_attempted_at` means the runtime entered the external dispatch
boundary. It does NOT claim the provider received the request. A crash
after started but without this marker resets to planned. A crash with
this marker transitions to unknown.

Rationale:
The runtime can only prove it crossed the dispatch boundary, not that
the OS sent bytes or the provider received them.

Depends_on: [INV-004]

Primary_enforcement: runtime_guard
  - Reconciler checks dispatch_attempted_at to classify started children

Defense_in_depth: none

Failure_codes:
  - N/A (reconciliation invariant)

Verified_by:
  - test_inv_011_started_without_dispatch_resets_to_planned
  - test_inv_011_started_with_dispatch_transitions_to_unknown

## INV-012: Exclusive Dispatch Ownership

Introduced: 2026-07-11
Status: ACTIVE
Scope: concurrency

Statement:
At most one concurrent execution reaches the external adapter per child
attempt. Dispatch ownership uses a fencing token (execution_claim_id)
for correctness and a separate expiring heartbeat for liveness.

Rationale:
Two concurrent EXECUTE_RETRY_AUTHORIZED commands must not both dispatch
the same external operation.

Depends_on: [INV-002]

Primary_enforcement: db_constraint
  - CAS on execution_claim_id in side_effect_ledger

Defense_in_depth: runtime_guard
  - RecoveryRuntimeGate verifies claim ownership before dispatch

Failure_codes:
  - CLAIM_ALREADY_HELD
  - CLAIM_EXPIRED

Verified_by:
  - test_inv_012_concurrent_commands_one_dispatch
  - test_inv_012_heartbeat_expiry_allows_reconciler_reset

## INV-013: Re-evaluation at Execution Time

Introduced: 2026-07-11
Status: ACTIVE
Scope: governance

Statement:
Current actor authorization, policy, contract compatibility, node/adapter
availability, and credential capability are re-evaluated at retry execution
time. A historical `safe_to_retry` decision grants eligibility to request
execution; it does not freeze governance.

Rationale:
A decision made days ago should not bypass a current policy denial.

## INV-014: Runtime Gate Matches Full Tuple

Introduced: 2026-07-11
Status: ACTIVE
Scope: side-effect recovery

Statement:
The Tier 1 runtime gate matches the tuple:
(side_effect_type, operation_name, adapter_id, adapter_version,
 request_hash, canonicalization_version).
For mutations, it also verifies the original idempotency identity and
namespace. Abort on first mismatch.

Rationale:
Without adapter_version and canonicalization_version, two implementations
could produce the same-looking operation name with incomparable hashes.

Depends_on: [INV-006]

Primary_enforcement: runtime_guard
  - RecoveryRuntimeGate.intercept() tuple comparison

Defense_in_depth: runtime_guard
  - Capsule digest verification

Failure_codes:
  - RETRY_REQUEST_MISMATCH
  - SIDE_EFFECT_RETRY_REJECTED

Verified_by:
  - test_inv_014_exact_match_dispatches

## INV-015: Legacy Rows Categorically Ineligible

Introduced: 2026-07-11
Status: ACTIVE
Scope: legacy migration

Statement:
Side-effect rows created without a pre-dispatch capsule are ineligible
for retry-authorized execution, regardless of when a later operator
decision is issued. v3.5 performs no replay-capsule backfill.

Rationale:
A v3.5 decision cannot prove what was dispatched pre-v3.5. Decision
recency and capsule provenance are separate facts.

Depends_on: [INV-004]

Primary_enforcement: runtime_guard
  - SideEffectRetryCoordinator checks capsule_status == available

Defense_in_depth: db_constraint
  - capsule_status column on side_effect_ledger

Verified_by:

## INV-016: Capsule Retention Tied to Lineage Closure

Introduced: 2026-07-11
Status: ACTIVE
Scope: data retention

Statement:
Capsule retention follows side-effect ledger retention and cannot expire
while retry lineage remains open. Run deletion is gated on lineage closure.
Per-run encryption keys are retained until deletion is permitted.

Rationale:

## INV-017: Lineage Chain Integrity

Introduced: 2026-07-11
Status: ACTIVE
Scope: lineage depth

Statement:
Retry lineage has no artificial depth limit. Each child enforces:
root_side_effect_key == parent.root_side_effect_key,
retry_ordinal == parent.retry_ordinal + 1,
parent_side_effect_key != side_effect_key,
no parent cycle, one child per recovery decision.

Rationale:
A depth cap of 2 buys nothing and creates arbitrary support burden.
The deterministic key scheme naturally supports arbitrary depth.

Depends_on: [INV-001, INV-002]

Primary_enforcement: runtime_guard
  - SideEffectRetryCoordinator._allocate_child_attempt() chain validation

Defense_in_depth: db_constraint
  - UNIQUE(run_id, recovery_decision_id)

Failure_codes:
  - LINEAGE_INTEGRITY_VIOLATION

Verified_by:
  - test_inv_017_grandchild_lineage_correct
  - test_inv_017_no_self_parent
  - test_inv_017_ordinal_increments

## INV-022: Invariants Ledger Append-Only

Introduced: 2026-07-11
Status: ACTIVE
Scope: process

Statement:
Safety and trace-truth invariants are maintained in a globally numbered
append-only invariants ledger. IDs are never renumbered or deleted.
Superseded invariants are marked REPLACED with cross-references.

Rationale:

## Implementation Decisions (DEC series)

These are v3.5 implementation choices, not timeless invariants. They may change in future releases without violating an invariant.

### DEC-001: Capsules stored inline in SQLite for v3.5

External blob storage deferred to v3.6. Max serialized capsule size 64KB. Canonical JSON with sorted keys. AES-256-GCM with per-run key. No truncation. Oversized = REPLAY_CAPSULE_OVERSIZED before planned→started.

### DEC-002: No authorization expiry or revocation in v3.5

Authorization binds to at most one child (INV-002). Current policy re-evaluated at execution time (INV-013). Expiry and revocation deferred to v3.6 ergonomics.

### DEC-003: No provider reconciliation in v3.5

Idempotency matrix: read-only → allow, mutation with reusable original idempotency identity → allow, everything else → block. Provider-specific non-execution reconciliation deferred to v3.6.

### DEC-004: No ancillary governed effects in v3.5

Tier 1 recovery permits one matching target side effect only. Read-only status does not grant an exception. Any non-target governed operation is rejected and traced. Ancillary-effect support, if required, will be designed in a later release.

### DEC-005: RecoveryEnvelopeV1 extends InvocationEnvelope

The recovery envelope is an extension of the normal InvocationEnvelope, not a parallel type. It adds recovery_mode, lineage identity, capsule reference, source binding, dispatch claim, and execution constraints. See plan file for the full schema.

### DEC-006: Adapter version matching is range-based

Semantic versioning ranges used everywhere (allowlist, runtime gate, capsule compatibility). Exact pinning is opt-in for adapters known to break on patch bumps.
