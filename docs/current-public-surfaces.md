# NodeChain Current Public Surfaces

**Document class:** Descriptive compatibility map  
**Baseline date:** 2026-08-18  
**Baseline SHA:** `78f98252173eb38d4284ed92f0fd3343c5c5ce21`  
**Released version:** `v3.6.0`

This document is the current companion to the historical `docs/frozen-surfaces.md` v1 compatibility contract.

`docs/frozen-surfaces.md` remains useful for identifying interfaces that were declared stable in the v1 era, but it is not a reliable inventory of every surface present in the current codebase. The live executable schemas, Click registrations, Python exports, and versioned contracts are authoritative for the exact baseline.

---

## 1. Compatibility principle

NodeChain distinguishes:

- **historically frozen compatibility commitments** — interfaces that existing users/packages may depend on;
- **current additive surfaces** — commands, schemas, APIs, and product capabilities added after the original freeze;
- **internal implementation seams** — modules/functions that are not public contracts merely because they exist in the repository.

An additive command or schema does not invalidate an earlier frozen surface. Conversely, an old document's command count must not be treated as the complete current surface.

---

## 2. CLI authority

The installed command tree generated by Click is the authoritative current CLI inventory:

```bash
nodechain --help
nodechain <group> --help
```

Major public families include, among others:

- runtime/run-state inspection and reconciliation;
- trust and trust-store operations;
- registry and node-package operations;
- recovery/operator actions;
- evaluation and certification;
- evidence and trace replay;
- deployment/release-history/drift/assurance operations;
- dashboards and console/graph tooling; compose plan validation (`compose validate`);
- local API server;
- governed review workbench;
- post-v3.6 Research Workspace commands.

Documentation should not maintain a hand-counted global command total unless it is generated from the installed CLI for a pinned release.

---

## 3. Core runtime contracts

The current runtime-facing compatibility concepts include:

- `InvocationEnvelope` / `EnvelopeResponse`;
- node manifests and contracts;
- typed semantic ports;
- chain blueprints;
- policy/trust enums and decision structures;
- state/trace schemas;
- side-effect lifecycle and recovery states;
- structured CLI exit codes.

Exact field-level compatibility is governed by the corresponding Python models, JSON schemas, invariant specifications, and released API commitments — not by this summary document.

---

## 4. Blueprint surface

Blueprints remain the declarative composition format for normal governed chain execution.

Current blueprint semantics include node definitions, typed connections, branch/join behavior, loops, review gates, invariants, policy/sandbox configuration, and other additive fields introduced after the original v1 freeze.

Use the current blueprint loader/models and schemas as the field-level authority. The abbreviated blueprint example in `docs/frozen-surfaces.md` should be read as a historical compatibility snapshot, not a complete current schema.

---

## 5. Trust and sandbox surface

Historical trust levels remain important compatibility identities:

```text
built_in
local_trusted
local_untrusted
remote_untrusted
```

Current execution behavior must additionally be read with `docs/deployment-profiles.md` (the canonical profile matrix), `BASELINE.md`, and `docs/linux-deployment.md` because trust identity and execution availability are distinct.

At the development baseline, ordinary POSIX `local_untrusted` / `remote_untrusted` execution through `SubprocessRunner.run_isolated()` routes into the supervised backend (H0.2). Enforcement requires a privileged Linux host; on every other platform or profile the invocation fails closed before workload start with `process_started=false`. The existence of a trust-level enum does not imply an enforced execution backend on every platform/profile.

---

## 6. Research Workspace surface

Post-v3.6 development adds a new CLI/product-proof family:

```text
nodechain research run
nodechain research review
```

and the `ResearchWorkspaceBundleV1` schema/reader/writer contract introduced through PR #12/#13.

These surfaces are **development baseline capabilities after v3.6.0**. They must not be back-projected into the v3.6.0 release record.

The current CLI review path has a documented descriptor/finalization integration gap; see `BASELINE.md`.

---

## 7. Local API surface

NodeChain includes a FastAPI local operator API, protected by bearer-token configuration and intended primarily as a local read-only control/inspection surface.

Its existence does not imply:

- hosted SaaS availability;
- multi-tenant identity/isolation;
- a general remote write/control API;
- enterprise connector authorization.

Those are separate roadmap outcomes.

---

## 8. Package and registry protocols

The SDK/registry layer includes additive versioned surfaces for:

- node/package manifests;
- lockfiles;
- certified registry entries;
- remote registry metadata/protocol;
- trust-store/signature material;
- evaluation/certification records;
- deployment/release assurance artifacts.

Where a protocol declares a schema/protocol version, that versioned artifact is the compatibility authority.

A package's digest/signature/certification/trust state must not be interpreted as automatic execution permission.

---

## 9. Exit codes

Structured CLI exit codes remain a public scripting surface. Code should import/use the named constants from `nodechain.cli.exit_codes`, and documentation for a command should describe command-specific meanings rather than inventing new ad-hoc process codes.

Historical exit-code commitments in `docs/frozen-surfaces.md` remain relevant unless superseded by an explicitly versioned compatibility decision.

---

## 10. How to change a public surface

Before changing a public command, schema, protocol, enum/state value, or package contract:

1. determine whether it is historically frozen/versioned;
2. locate compatibility tests and consumers;
3. classify the change as additive, compatible correction, deprecation, or breaking;
4. update the authoritative model/schema first;
5. add migration/compatibility behavior where required;
6. update `BASELINE.md` only if the current product/architecture claim changes;
7. record released compatibility changes in `CHANGELOG.md`/release notes when the release is cut.

The goal is not to freeze every internal function forever. It is to know which surfaces users, packages, automation, and persisted artifacts are entitled to rely on.
