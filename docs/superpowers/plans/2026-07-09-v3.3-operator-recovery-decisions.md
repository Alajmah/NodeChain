# Operator Side-Effect Recovery Decisions (v3.3.0) Implementation Plan

**Goal:** Wire governed operator resolution for crash-window `unknown` side effects. Operators list unknown effects and resolve them via `RESOLVE_SIDE_EFFECT`, which atomically records a recovery decision and transitions the side-effect ledger through the existing semantic-binding gate. No autonomous recovery, no skipped-node re-execution, no validator relaxation, no `waived` status.

**Architecture:** Three layers. (1) Store foundation: a new transactional `resolve_side_effect_recovery_decision_transactional` method on `DecisionLogStore` that INSERTs the decision + runs the gate + UPDATEs the ledger in ONE transaction (plain INSERT, not INSERT OR REPLACE; PK constraint enforces uniqueness). (2) `StateManager.resolve_side_effect_recovery_decision` facade with validation (status==unknown pre-check, evidence requirements, clean errors). (3) `RecoveryAction.RESOLVE_SIDE_EFFECT` + RBAC + `RecoveryService._delegate_action` + CLI.

**Design basis:** `docs/design/recovery-decision-authority.md` (converged, code-verified).

**Tech Stack:** Python 3.11+, sqlite3, Click CLI, pytest. No new dependencies.

## Locked non-goals
No autonomous recovery · no automated agent · no `waived` status · no skipped-node re-execution · no retry execution after `safe_to_retry` · no run()/resume() control-flow change · no observed-completion validator relaxation · no unknown→completed via `output["side_effect_records"]` · no Model B · no new broad trace vocabulary.

## Implementation guardrail (from user)
**Do not pre-check duplicate IDs as the only defense.** Use plain `INSERT`; let the PRIMARY KEY constraint raise `sqlite3.IntegrityError` inside the transaction; translate to `DUPLICATE_RECOVERY_DECISION`.

**Files:** `src/nodechain/core/stores.py` (add method to `DecisionLogStore`), `tests/test_side_effect_recovery_decisions.py` (add tests).

- [ ] Add `resolve_side_effect_recovery_decision_transactional(self, decision: dict, target_status: str, response_hash=None, external_reference=None) -> None` to `DecisionLogStore`. One `sqlite3.connect`; INSERT decision (plain INSERT, not INSERT OR REPLACE); then run the gate logic + UPDATE inline (mirroring `update_side_effect_status` lines 315-395 but on the same conn, so the freshly-inserted decision is visible to the gate's SELECT).
