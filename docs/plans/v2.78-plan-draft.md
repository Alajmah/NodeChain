## ChatGPT's three corrections (accepted)

1. **Side channel: parent-created pipe, FD passed in config — NOT hard-coded fd 3.**
   `rfd, wfd = os.pipe()`; parent passes `pass_fds=(wfd,)` and `config["metadata_fd"] = wfd`.
   Avoids fd-number assumptions, more portable, invisible to workload after close.

2. **Canary expectation: SIGSYS/kill, NOT OSError/EPERM.**
   The NodeChain profile uses `KILL` action (default). `os.fork()` inside the
   workload terminates the process via SIGSYS, NOT raise OSError. Parent-side
   classification of SIGSYS (via wait status) is the correct proof. The v2.77
   test's OSError assumption was wrong and would have failed for the wrong reason.
   Do NOT change the production profile to ERRNO just to make the assertion nicer.

3. **Python startup: test `-I -S -c` first; do NOT loosen the profile preemptively.**
   Empirical gating. If minimal Python startup trips clone (unlikely for `-I -S`),
   treat as a blocker and fall back to a compiled C helper — but test Python first.

## Thesis

Prove that NodeChain can enforce syscall filtering at the correct execution
boundary (the workload) while preserving the command-runner model. The v2.76
model applied seccomp to the *spawner* before `subprocess.run` — incompatible
with the deny-list because the spawner must fork. v2.78 moves seccomp to the
*child*, applied after all setup, immediately before in-place `execve` into the
workload. The filter survives `execve` (standard Linux behavior — seccomp
filters attach to the process, not the binary), so the workload runs confined
without the spawner needing fork-denied syscalls.

## The one architectural question

*Can NodeChain enforce syscall filtering at the correct execution boundary
while preserving the command-runner model?*

Answer: yes, by applying the filter to the child process after setup and
`execve`-ing the workload in place. No fork/clone is needed after seccomp
because there is no grandchild — the child becomes the workload.

## Model (refined from reviewer feedback — load-bearing)

The current model breaks under `execve` because the Python bootstrap is
replaced by the workload and cannot return to assemble JSON. The new model:

```
parent / native runner (supervisor)
  - spawns ONE child (the bootstrap) via asyncio.create_subprocess_exec
  - owns stdout/stderr capture (workload output = child's stdout/stderr)
  - owns timeout + final result normalization (exit code, output cap)
  - reads setup metadata from a SIDE CHANNEL (not stdout)

bootstrap child (Python, spawned by parent)
  1. enters PID/network/mount/chroot/procfs boundary (proven in v2.77)
  2. writes setup metadata to side channel
  3. applies seccomp to SELF (process-local filter)
  4. writes seccomp_applied metadata to side channel
  5. os.execve() workload argv IN PLACE — replaces self with workload

workload (the argv, e.g. [python, -c, probe])
  - inherits the seccomp filter (survives execve — Linux guarantee)
  - emits normal stdout/stderr only
  - for enforcement tests: emits a probe result (e.g. fork canary blocked)
```

### Side channel mechanism (ChatGPT-agreed: parent-created pipe, FD in config)

```python
# parent
rfd, wfd = os.pipe()
proc = await asyncio.create_subprocess_exec(
    sys.executable, "-c", child_script,
    stdin=..., stdout=..., stderr=...,
    pass_fds=(wfd,),   # only the write end
)
config["metadata_fd"] = wfd

# child
metadata_fd = cfg["metadata_fd"]
# write NDJSON metadata events to metadata_fd
os.close(metadata_fd)   # before execve
```

Reasons (ChatGPT): avoids stdout pollution; invisible to workload after close;
survives chroot (fd is in-kernel); avoids exposing /metadata.json inside chroot;
gives parent authoritative setup metadata even after execve replaces bootstrap.
Parent owns final result assembly from: child exit status, stdout, stderr,
side-channel metadata, timeout classification.

## Non-negotiable invariant (reviewer constraint)

After seccomp is applied, the bootstrap must NOT call `subprocess.run`,
`Popen`, or anything that may internally fork/clone. The only allowed
transition is in-place `os.execve`. Enforced by phase ordering: namespaces →
chroot → seccomp → execve (terminal).

## Phase ordering in the child

```
0.   read config from stdin (parent → child)
1.   PID namespace (requires fork — DONE BEFORE seccomp)
1a.  procfs remount
2.   network namespace
3.   mount namespace
4.   mount confinement + chroot (with extra_mounts for /usr, /lib, /lib64, venv — proven in v2.77)
5.   write setup metadata {pid, net, mount, chrooted_workspace_prefix} to fd 3
6.   apply seccomp filter to SELF (deny fork/vfork/clone/clone3/ptrace/...)
7.   write seccomp metadata {seccomp_applied: true, seccomp_apply_mode: child_pre_exec} to fd 3
8.   close fd 3
9.   os.execve(argv[0], argv, env)  — TERMINAL; bootstrap is replaced
```

Note: PID namespace (step 1) uses a two-stage fork internally and MUST happen
before seccomp (step 6) — fork is denied post-seccomp. This is the load-bearing
ordering constraint.

without claiming workload-level verification.

## Linux semantics note (the mechanism that makes this work)

seccomp filters installed via `prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, ...)`
or `seccomp(2)` attach to the *process*, not the binary. They survive across
`execve` (this is how runc/containerd confine workloads: init applies the
filter, execve's the container process, the process is confined). So the
bootstrap's self-applied filter confines the workload after execve without the
workload needing to cooperate. No `SECCOMP_FILTER_FLAG_TSYNC` is required
(single-threaded bootstrap at apply time).

## Risks (open for ChatGPT)

1. **fd 3 lifecycle across execve** — fd 3 must be close-on-exec OR explicitly
   closed by the bootstrap before execve. If it leaks into the workload as an
   open fd, that's a minor cleanliness issue (workload sees an unexpected open
   fd) but not a security issue. Mitigation: set FD_CLOEXEC on fd 3 in the
   bootstrap, OR write-and-close before execve.
2. **The probe workload itself needs to import os/sys to attempt fork** — those
   imports happen AFTER seccomp is applied. seccomp denies syscalls, not
   imports, so this is fine — but worth noting that the workload's Python
   startup must not need a denied syscall (Python startup does use clone for
   threading on some platforms; need to verify Python 3.12 single-threaded
   startup doesn't trip the filter).
3. **PID namespace's two-stage fork** happens at step 1, before seccomp at step
   6 — correct ordering, but if a future refactor moves seccomp earlier it
   breaks. Worth a code comment at the seccomp site.
