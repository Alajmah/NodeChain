## Evidence Synthesizer Failure Analysis

### What the node received

- 56 qualified sources (all passed quality evaluation, avg score 0.58)
- Each source has: source_id, title, authors, abstract (~1000 chars),
  doi, citation_count, venue, subject_areas, credibility_signals
- Memory context: not used (no prior session memory)

### What the node produced

```json
{
  "claims": [],
  "synthesis": {
    "summary": "Unable to synthesize evidence due to processing error.",
    "key_findings": [],
    "areas_of_agreement": [],
    "areas_of_disagreement": []
  },
  "source_count": 56
}
```

### Likely failure modes (to be diagnosed in Phase 1)

The generic "processing error" message comes from the synthesizer's
fallback catch block — it fires when `response.structured_output` is
None AND `json.loads(response.content)` raises `JSONDecodeError`. This
means one of:

1. **Model produced empty or non-JSON output** — Gemma 4 12B may have
   hit output token limits with 56 sources × ~500 char abstracts in the
   prompt (estimated ~30K chars of source data + JSON schema instructions)
2. **JSON parsing failure** — model may have produced JSON inside markdown
   fences or with formatting issues that `_extract_json` couldn't handle
3. **Context window overflow** — the full 56-source payload may exceed
   the model's effective context window for structured generation
4. **Adapter response shape mismatch** — the pre-fix LIMModelAdapter
   may have returned a response shape the synthesizer didn't expect

### Phase 1 diagnostic plan

```
1. Preserve exact synthesizer input from this run
2. Run synthesizer node in isolation with fixed ModelAdapter
3. Capture raw model response (content, structured_output, usage)
4. If content is empty: likely token limit or context overflow
5. If content exists but unparseable: fix JSON extraction
6. Test with reduced source sets (8, 20, 56 sources)
7. Compare Gemma vs qwen3.5-27b with same inputs
```
